## 二、四个高危问题与修法

### 问题 1 🔴 制图完全没有金额闸门（"无确认即扣费"）

**实测证据**：调用 `qwen_draw` 时**不传任何确认参数**，直接出图并扣费 ¥0.18。
代码层面：`spend-guard.mjs` 写着"**任何付费路径都必须先过这里**"，
但全仓 `authorizeSpend/estimateSpend` 只被 `seedance-video.mjs` 引用；
`tools/qwen-draw.mjs` 只有次数预算 `budget.take`。`index.js` 里也只有两个 video 上限。
后果：未计价 / 零价的制图模型照常提交；0.18×4 张×6 次/25 秒窗口 ≈ ¥4.3/窗口 ≈ ¥10/分钟无人拦。

**修法**（不动 schema 形状、不新增配置项）：`qwen_draw` 复用同一套三层闸门。

```js
const estimate = estimateSpend({ model: spec.model, duration: spec.n, unitPrice: unitPriceOf(...) })
const verdict = await authorizeSpend({
  estimate, config,
  noun: '出图', unitLabel: '张',          // 文案按"张"计价，默认值保持出片文案逐字不变
  spentInSession: () => sessionSpentOrThrow({ getLedger, sessionId, providerLabel: 'DashScope' }),
  confirmed: { confirm_estimate: args.confirm_estimate, confirm_unpriced: args.confirm_unpriced },
})
if (!verdict.ok) throw new MediaError(CODES.BAD_REQUEST, verdict.message)
```

- 参数只加两个（`confirm_estimate` / `confirm_unpriced`），描述压到最短；
- 上限沿用 `videoCostLimitCNY` / `videoSessionCostLimitCNY`（两个字段的说明文字改为"出片/出图"）；
- **缓存命中不需要确认**（本来就没花钱，不再多一道手续）——已写成断言。
- 代价如实记：`qwen_draw` schema **538 B → 691 B**（+153 B/请求，≈+38 token）。

### 问题 2 🔴 任务注册表的 storage 后端是死的（实机自报降级）

**实测证据**：同一时刻 `media_task(action=list)` 报「注册表后端：**file**」，
而 `media_report(health)` 报「账本后端：**storage**」——同一个宿主服务，一个成一个败。

**根因**：账本用的是宿主契约 `defineDomain({...})` + `domainTable(zod)`（所以它成），
注册表传的是**裸 JSON-Schema 对象** `{ tasks: { key: 'id', schema: {...} } }`，`open()` 直接抛错 →
静默退回 JSON 文件；即便侥幸打开，旧 schema 里 `id` 是 `required` 而代码**从不写 id**（表键是 `provider:taskId`），
任何已存记录都会在下次 `open()` 校验失败。读路径还调了宿主 KvTable 没有的 `.all()`。

**修法**：与账本同源——`defineDomain` + `domainTable(zod)` + `invalidRecords: 'backup-and-skip'` +
`[...table.entries()]`；schema 按**实际写入字段**逐个列出（at/provider/taskId/model/prompt/n/mode/duration/status）。
并把"降级到 file"的原因**写进 health 报告**（以前只有一句 `file`，用户没有任何线索）。

### 问题 3 🔴 会话累计上限看不到已经花掉的钱

两处成因，分别修：

1. **静默 fail-open**：`spentInSession` 在账本打不开时 `catch { return 0 }` →
   等于无声关掉会话累计上限。现在改为 `sessionSpentOrThrow`：读不到就**拒绝提交**，
   错误码 `UNAVAILABLE`，文案明确"本次未产生任何费用"。
2. **记账时机**：成功路径的记账在产物落盘之后，于是 TIMEOUT / ABORTED（远端已计费）之后账上是零，
   "反复提交完就放弃"永不触顶 —— 正是 2026-10-15 事故的形态。
   现在超时/取消会补记一笔**预估**（`accountUnretrievedSpend`），
   带 `note` 标明是预估，并**按 taskId 去重**（之后用 `media_task(download)` 补回产物不会重复计费）。

**仍未覆盖的边界（如实记）**：整轮请求中途失败（进程/轮次直接死掉）时工具自己没机会记账；
那时只能靠注册表（本次已修好）把 task_id 留下来人工补下载。

### 问题 4 🔴 运行时跑的是旧模块

插件在 DSH 启动时加载，改代码不会热重载。本轮的改动**需要重启 DSH 才生效**。
本文所有"生效"结论均来自离线套件 + 变异测试的源码级验证；运行态复验要在重启后做。

## 五、（追加）小额免确认阈值 `noConfirmUnderCNY`

**动因**（用户提出）：确认流程天然是两次调用（先报价、再复述金额），
而制图单张 ¥0.18、一批最多 4 张（¥0.72）—— 每出一批图都多一轮往返，效率太低。

**改法**（新配置项，默认 1 元，**设置卡里可改**）：

```js
const noConfirmUnder = capOf(config.noConfirmUnderCNY)
if (noConfirmUnder !== null && estimated <= noConfirmUnder) return { ok: true }
```

- **位置是关键**：放在**单次/会话两个上限之后**、确认层之前。
  放错到上限之前，它就变成"绕过上限的后门"——变异测试 `小额免确认改成不看金额` 就是专门注入这个错误，
  由 `单次上限与会话累计上限同样管制图（阈值再大也绕不过上限）` 这条用例抓住。
- **只跳过第 3 层**：单次/会话上限照旧；**未计价照旧 fail-closed**（未计价在函数开头就返回，走不到阈值）。
  用例里阈值故意开到 10 元来证明"调大阈值救不了未计价"。
- **默认值的边界**：1 元正好覆盖制图任何一批（≤¥0.72），而出片 1 秒就是 ¥1.52 → **出片仍然每次都确认**（用例钉住）。
  `0` = 关闭该机制，一律确认。
- 免确认 ≠ 不记账：账本照旧记录（用例断言 amount=0.72 / units=4）。
- 设置卡新增一个数字项（中文/英文标签都补了；`client.js` 的 i18n 键闭合用例仍全绿）。

**性能影响**：工具 schema 不变（这是 Config 字段，不进每请求的工具表）。

   把设置卡里的 `noConfirmUnderCNY` 调成 `0` 后，同样的调用才会先报价、等你复述金额。

   而不是照常花钱。
