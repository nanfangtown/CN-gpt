# 第一部分：性能（本次的重点）

## 结论先行

**CPU 开销可以忽略，真正的成本是"每个请求都要发送的 JSON 体积"。**

| 开销 | 实测 | 判断 |
| --- | --- | --- |
| guard 链（普通工具调用） | **0.0005 ms/次** | 可忽略，**不需要优化** |
| guard 链（读图员，日志 5000 条） | 0.062 ms/次 | 可忽略 |
| 提示词段落 | **710 B ≈ 159 token/请求** | 每轮都发 |
| 4 个工具 schema | **2777 B ≈ 835 token/请求** | 每轮都发 ← **主成本** |
| 每秒对账（1000 会话） | 2.283 ms/s → **0.001 ms/s** | **已修，2000 倍** |

对照量级：一次真实工具调用 **50 ms**、一次 LLM 往返通常 **1000+ ms**。
所以 guard 链那 0.0005 ms 完全淹没在噪声里——**这一节的结论就是"不用优化这里"**。

## 优化 1：工具 schema 3342 B → 2777 B（-17%）

工具定义随**每个请求**发送，所以参数描述是**持续成本**，不是一次性成本。

根因是我自己上一轮写胖的：`seedance_video` 一个工具 1663 B，其中两个确认参数
写了近 600 B 小作文（`confirm_unpriced` 一个就 **377 B**）。

| 工具 | 优化前 | 优化后 |
| --- | --- | --- |
| `qwen_draw` | 538 B | 538 B |
| **`seedance_video`** | **1663 B** | **1098 B（-34%）** |
| `media_task` | 721 B | 721 B |
| `media_report` | 420 B | 420 B |
| 合计 | 3342 B | **2777 B** |

正文该写进 README，不该写进**每个请求都要发**的工具表。
现在测试里钉了字节预算，防止以后又写胖。

## 优化 2：每秒对账 1000 会话 2.283 ms → 0.001 ms（约 2000 倍）

`syncRestrictions()` 每秒跑一次，原来为**每个存活 agent** 重算"该 deny 哪些工具"，
每次都新建一个 deny 数组。会话一多就是持续 CPU 与持续垃圾回收。

| 存活会话 | 修复前 | 修复后（稳态） | 开关真变化时 |
| --- | --- | --- | --- |
| 1 | 0.003 ms/次 | 0.001 ms/次 | 0.005 ms/次 |
| 50 | 0.119 ms/次 | 0.001 ms/次 | 0.079 ms/次 |
| 200 | 0.509 ms/次 | **0.001 ms/次** | 0.331 ms/次 |
| 1000 | **2.283 ms/次** | **0.001 ms/次** | 1.323 ms/次 |

修法：开关状态做**字符串签名**，签名没变就整轮跳过。
稳态固定成本只有 6 次配置读取，**与会话数无关**；
开关真被改到时签名立即可见，下一个 tick（≤1 秒）照旧完成对账。

> ⚠ 这是个**会吞掉配置变更**的优化。所以配了正确性测试：连跑 5 次 tick 不许重复贴掩码，
> 但改开关后**必须**在一次 tick 内把掩码跟上——那正是这个插件 2026-10-13 修过的老毛病。

## 没做的事，以及为什么

- **没有优化 guard 链**：实测 0.0005 ms，优化它没有意义。
- **没有改 `isConcurrencySafe`**：核对宿主契约（`@deepseek-ai/dsh-tools`：独立只读调用可并发，
  mutating 调用单独跑、按提交顺序串行）后确认当前分类是对的——
  `qwen_draw` / `seedance_video` 付费提交必须串行，`media_task` 的 `download` 会写文件，
  `media_report` 纯读且有 TTL 缓存所以标 `true`。
- **没有缩减提示词段落**：710 B 是 4 行实用策略；想省可以 `promptSection: false` 整段关掉。

# 第二部分：三个故障的修复

## 故障 1 🔴 模型 id 换了、单价表的键没换 → 出片被闸门锁死

`seedanceModel` 改成 `doubao-seedance-2-5-260628` 后，`pricing` 里**只有旧键** `seedance-2.0`，
查不到价 → 花费闸门走"未计价"分支 → 确认层要一个算不出来的金额 → **fail-closed，工具不可用**，
且**全程零告警**。根因是 `pricing`（字典）与 `seedanceModel`（字符串）互相独立、无外键校验。

**修法**：出厂表补齐三个真实模型 id；新增 `pricingWarnings()` 自检，在**启动日志**与
**`media_report(health)` 的「单价表」段**同时点名。

## 故障 2 🔴 单价写成 `0` → 真钱显示成免费

`qwen-image-3.0: unitPrice: 0` → 已生成的 16 张图报 `0.0000 CNY`。
代码只在 schema description 里警告过，而 `z.dict(z.any())` 收得下任何值，
本项目实测的 schemastery 3.18.4 **没有 `.refine()`**，schema 层拦不住。

**修法**：`zeroPriceOverrides()` 严格区分三种情况——

| 写法 | 含义 | 是否报 |
| --- | --- | --- |
| `unitPrice: 0` | 宣称"免费" | ✅ 报 |
| `unitPrice: null` | 未计价 | ✅ 报（覆盖了出厂价时） |
| `unitPrice: 0.5` | 我自己的合同价 | ❌ 不报 |

## 故障 3 🟡 未计价时，闸门可被一句话绕过

初版"只要 `confirm_estimate` 是数字就放行"→ 调用方报 `confirm_estimate: 1`
就能推开闸门，单次/会话上限**一并跳过**。

**修法**：fail-closed。`allowUnpricedSpend`（默认 false）一律拒绝且**不接受自报金额**；
打开后仍须 `confirm_unpriced: true`。
